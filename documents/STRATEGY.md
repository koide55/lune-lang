## 1. Lune に入っている「新しい概念」の棚卸し

Lune は直近10年の PL 研究・言語 UX 研究の成果を小さな言語に凝縮した構成になっている。

| Lune の機能 | 研究・実務上の系譜 |
| --- | --- |
| 網羅性検査+反例 (witness) 提示 (TYP0007) | OCaml/Rust の網羅性検査。反例を診断に出すのは比較的新しい実装水準 |
| フロー依存の null 安全 (`T?`, `?.`, `??`, 条件 narrowing) | Kotlin/TypeScript 系の flow typing |
| 期待型伝播による局所型推論 (TYP0010/0011) | bidirectional typing の実用形 |
| 全診断コードに教材的解説 (`lune explain`) | Rust の `--explain`/error index の発展形。「全コードに解説がある」ことをテストで強制しているのは独自性が高い |
| did-you-mean + `lune fix` (機械適用可能な修正) | Rust の rustfix、LSP の code action 系譜 |
| 正準フォーマッタ `lune fmt` (冪等性・意味保存を再パースで検証) | gofmt 以降の「議論を終わらせるフォーマッタ」文化 |
| デフォルト遅延+明示的 strict (`strict`/`seq`/`force`) | Haskell の遅延評価を「観察可能・opt-out 可能」に再設計 |

この組み合わせは偶然ではなく一つの軸に収束している: **コンパイラが学習者に教える**。

## 2. 「多くの人に」の現実 — 新言語の採用経路は3つ

汎用言語としての普及競争 (エコシステム・ライブラリ・求人) は、個人開発の言語には構造的に勝ち目がない。現実的な入口は次の3つで、Lune の資産は (a) と (c) に強く適合する。

- **(a) 教育**: 講義・独習で「概念を学ぶための言語」として使われる (Racket、Pyret、Hedy の経路)
- **(b) ホビイスト/言語愛好家**: 面白い言語として遊ばれる (Gleam 初期、Zig 初期)
- **(c) 研究コミュニティ**: 論文・実装として引用される

## 3. ポジション: 「エラーが教材になる、日本語話者のための関数型入門言語」

競合状況にはっきりした空白がある。

- **Haskell**: 遅延評価の本家だがエラーメッセージが初学者に敵対的
- **Elm**: friendly errors の元祖だがフロントエンド専用で、概念教育には範囲が狭い
- **Racket/Pyret**: 教育言語として確立しているが S 式系/英語圏中心
- **Hedy**: 多言語化 (母語でエラーが読める) で成功したが、対象は初等教育・手続き型

「**ML 系の型・ADT・パターンマッチ・遅延評価を、母語で教えてくれるコンパイラで学ぶ**」という位置は空いている。教科書が日本語と英語の両方で読め、遅延評価に丸ごと1章（第4章）を割いていることが、この位置取りの実体である。

さらに、**デフォルト遅延がこの空白を広げる**。教育言語 (Racket/Pyret/Hedy) はすべて正格であり、遅延評価の本家 Haskell は教育向けの診断を持たない。「評価戦略そのものを教えられる言語」という象限には競合がいない。デフォルト遅延は初学者への罠と見なされがちだが、Lune はこれを診断と可観測化 (施策 E) で教材に転化する — この設計上の緊張とその解決こそが、研究発表 (施策 D) の中心的な主張になる。

キャッチコピー: **Lune — the Lazy and Native programming language**。Lazy = デフォルト遅延 (施策 E)、Native = 母語 (native language) 診断 (施策 B) の掛詞で、名前の L と N にも掛かる。PL の文脈で "native" はネイティブコード生成と読まれがちだが、発表ではその誤読を逆手に取れる — 「native code ではなく **native language**」と種明かしするつかみは PRO の導入に向く。補助案: *the functional language whose compiler teaches you* / 「コンパイラが教えてくれる関数型言語」

## 4. 施策の優先順位 (インパクト × コスト)

### A. ブラウザ Playground (最優先・効果最大)

新言語の最大の離脱点はインストールである。実装が Pure Python であることは、**Pyodide (ブラウザ内 Python) でそのまま動かせる**ため普及上の武器になる。URL 一つで REPL+`explain`+診断表示が動けば「親しんでもらう」コストがゼロになる。あわせて `pip install` / `uvx lune` での配布も低コストで可能。

技術検証 PoC は `playground/` にある (検証結果は `playground/README.md`)。GitHub Pages での公開も実装済み: `.github/workflows/pages.yml` が main への push でリポジトリ全体をデプロイし、ランディングページ (`index.html`)・Playground・診断カタログ (`playground/errors.html`)・教科書 (`book/`、HTML と PDF。2026-09-08 に追加) が 1 つの URL 配下で公開される。

「URL 一つで REPL が動く」という本項の目標は 2026-07-26 に達成した。Playground の右カラムに REPL タブがあり、端末と同じ `lune.repl.ReplSession` を駆動する (セッション保持・全 `:` コマンド・複数行入力・履歴・エディタからの読み込み)。

2026-09-08 に残件を片付けて本項は完了とする。教材 (チュートリアル・教科書) からの「Playground で開く」導線が付き、モジュール (`import`) を含むプログラムもファイルタブで動くようになった。後者に処理系側の変更は要らなかった — モジュール解決は入口ファイルのディレクトリを探索するので、Pyodide FS の `/app` に並べて書くだけで済む。残っているのは REPL 側の `import` 解決だけで、これは Playground ではなく `ReplSession` の制限である。

### B. 診断メッセージの日本語化 (差別化の核)

`explanations.py` は全診断コードのカタログ構造を既に持つため、`--lang ja` は設計変更なしで載る。「エラーも解説も母語で読める関数型言語」は Hedy が初等教育で証明した効果を関数型教育に持ち込むもので、研究的新規性 (施策 D) と普及施策が同じ作業で手に入る。費用対効果が最も高い一手。

実装済み: 全31コードの日本語詳解 (`lune/explanations_ja.py`、英語カタログとのコード集合一致をテストで強制)。`lune explain <CODE> --lang ja`、REPL `:explain CODE ja`、Playground の言語セレクタ、`documents/ERROR_INDEX_JA.md` (自動生成・同期テスト付き)。診断メッセージ本文も実装済み: 全 raise サイト（約110箇所）を `lune/messages.py` のカタログ (`t(key, **params)`) 経由に移行し、メッセージ・caret 注・hint・`= help:` フッタまで日本語化した。入口は CLI グローバル `--lang ja`、REPL `:lang ja`、Playground の言語セレクタ。キー網羅・未使用ゼロ・対訳パリティはテストで強制。これで施策 B は完了。

### C. エラー駆動学習への再編

チュートリアルに「わざとエラーを起こす → 診断を読む → `explain` で理解する → `fix` で直す」という節を組み込み、診断カタログ (全コードの解説) を Web で公開する (Rust error index 相当)。「診断こそが教材」という主張を製品自体で示す。

実装済み: チュートリアル第17章「エラーを読む、エラーから学ぶ」(日英) — 診断の解剖学、typo/網羅性/実行時の3周、「指定した診断をわざと出す」逆転演習。診断カタログは `documents/ERROR_INDEX.md` (`lune explain --index` で自動生成、テストで同期を強制)。Web 公開も実装済み: `playground/errors.html` が生成済み Markdown (日英) をその場でレンダリングし、GitHub Pages で配信される。

教科書ではこれをさらに厚く実装した (2026-07-26)。第11章「エラーと対話する」が丸ごとエラー駆動開発の章で、各章にも「壊してみよう」を置いてある。つまり施策 C の主戦場は、いまはチュートリアルではなく本の側にある。

### D. 研究発信という増幅器

講義や演習で小規模に使って学習効果を測れば、SPLASH-E・ITiCSE、国内なら PPL・情処 PRO に出せる題材になる。論文・発表は教育言語にとって最良の広報チャネルでもある (Hedy・Pyret が実例)。

特に PRO では、**デフォルト遅延をうまく位置づけると評価がむしろ高くなる**。「親切なエラーメッセージの教育言語」だけでは工学的貢献に見られやすいが、「**遅延評価をデフォルトにしたまま初学者に教えられるか**」という設計課題への解答として提示すれば、言語設計の研究貢献として立つ。発表可能な題材:

- **可観測な遅延評価の設計**: 明示的 opt-out (`strict`/`seq`/`force`/`deepForce`)、成功と失敗の両方のメモ化、ThunkState による再帰サンク検出 — GHC が `<<loop>>` で突き放すところを、コード付き診断+`explain` の教材にできる (現状は汎用 RUN0006 に集約されており、専用コードへの昇格は施策 E の作業項目)
- **全診断コードに教材解説をテストで強制する設計** (`tests/test_explanations.py`)
- **witness 付き網羅性診断** (TYP0007) の教育効果
- 診断の多言語化 (施策 B) の設計と効果測定

### E. 遅延評価の可観測化 (研究の柱)

デフォルト遅延は Lune の最大の差別化点であり、施策 D の中心的な研究主張を支える実装でもある (§3)。「初学者への罠」という一般的な批判への Lune の解答を、道具として作る:

**道具は3つとも実装済み** (2026-07 中に完了。以下は実際の出力):

- **REPL での thunk 可視化** — `:thunks [NAME]` が束縛の状態を、評価を起こさずに表示する。未評価・評価済み（値付き）に加え、**失敗もメモ化されていることが見える**:

  ```text
  lune> :thunks b
  b : unevaluated
  lune> b
  error[RUN0006]: division by zero
  lune> :thunks b
  b : failed = error[RUN0006] division by zero
  ```

- **評価トレース** — REPL の `:trace on|off` と CLI の `--eval NAME --trace`。force の入れ子を字下げで示す
- **遅延評価固有の診断コード** — 再帰サンク検出は汎用 RUN0006 から専用の **`RUN0005`** に昇格済み。`lune explain RUN0005` は「計算の前にサンクへ『評価中』の印を付ける。ループして同じサンクを再び force したら自己参照だと分かる」という仕組みと、`def` の再帰はなぜ問題ないのかまで説明する

**教材との連動も 2026-09-08 に完了**: 教科書第4章のコード例から「Playground で開く」で飛べる。Playground 側の道具（トレースのチェックボックス、REPL タブの `:thunks`）と、そこへ導く線の両方が揃った。

### F. 見せ方の整備 (低コスト)

README は現在「実装済み機能の羅列」で、初見の人に物語が伝わらない。「コンパイラが教える関数型言語」を冒頭に置き、エラー表示のスクリーンショットを最初に見せる構成へ。公開を強く意識する段階になったら、リポジトリ名を `lune-lang` 等へ変える選択肢もある (GitHub はリネーム後も旧 URL をリダイレクトする)。

実装済み (2026-07-21): README を学園青春ものの物語構成に全面刷新 (設定は koide 提供: 全員部活必須の校則、楽そうだと思ってプログラミング部に入った男子転校生が、先輩たちに鍛えられる)。部訓「必要になるまで、やらない。一度やったことは、忘れない」= 遅延評価+メモ化。先輩たち = ツールの擬人化 (真知部長 = match/型チェッカ、英美先輩 = explain/日英切替、直美先輩 = fix/fmt)。冒頭はタグライン・Playground 導線・日本語診断のヒーローサンプルで、掲載出力はすべて実機検証済み。リポジトリ名も 2026-07-21 に `Progamming-Language-Lune-001` から `lune-lang` へ変更済み (旧 git/Web URL はリダイレクトされる。GitHub Pages の URL のみ https://koide55.github.io/lune-lang/ に変わる)。これで施策 F は完了。

## 5. やらないこと

`LANGUAGE_FUTURE_SPEC.md` の Phase 2〜4 (JVM 連携・OO・実用化) は、この戦略では**当面凍結**する。Java 相互運用は「実務採用」を狙う施策だが、それは勝ち目の薄い戦線であり、教育ニッチには Python インタプリタの速度で十分。性能最適化・パッケージ管理も優先度を下げる。

デフォルト遅延を「やめる」ことも、当然しない。初学者には罠になり得るという一般的な批判には、隠すのではなく可観測化 (施策 E) で応える。これは妥協ではなく、教育ポジションと研究ポジション (施策 D) の両方を支える中心的な設計判断である。

## 6. 検証方法

「親しんでもらえたか」は GitHub スター数より次で測る。

- Playground の到達数と滞在、教科書の読了率（第4章まで到達したか）
- 講義で使った際の理解度・つまずき箇所 (そのまま論文のデータになる)
- `explain` がどのコードで参照されるかの分布 (匿名で取れれば診断改善の優先順位になる)

## 7. 要約

汎用普及は狙わず、「**母語で教えてくれるコンパイラを持つ関数型入門言語**」に集中する。当初の次の一手 (1) Pyodide Playground、(2) 診断の日本語化、(3) エラー駆動チュートリアル、(4) 遅延評価の可観測化は、**いずれも道具として実装を終えた**（§0）。

そのうえで打った次の一手が「**作った道具に、教材から線を引くこと**」だった。`:thunks` も `:trace` も Playground も本もあるのに、学ぶ人がその順に辿れる導線がなかった。教科書とチュートリアルのコード例から「Playground で開く」で飛べるようになり、その Playground が `import` で分けたプログラムも動かせるようになった 2026-09-08 をもって、施策 A・E とも完了とする（§0）。実装として残っているのは、この文書の外にある個別の課題だけである（REPL の `import` 解決 = issue #107 など）。

デフォルト遅延は隠すべき弱点ではなく、教育・研究両面の中心的な差別化点として前面に出す。研究発表を広報チャネルとして使い、JVM/OO 路線は凍結する。
